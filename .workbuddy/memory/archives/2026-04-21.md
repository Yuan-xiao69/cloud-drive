## 修复仓库页面空白 bug

### 根本原因
仓库页面加载时调用了 `/api/repos/[username]/[repoName]/issues` 和 `.../pulls`，这两个 API 返回 500，因为：
- `prisma.issue` 和 `prisma.pullRequest` 不存在——Prisma Schema 里没有这两个 model
- 数据库里也没有对应的表

### 修复过程
1. 在 `prisma/schema.prisma` 中添加了 5 个新模型：
   - `Issue`（含 `IssueComment`、`IssueLabel`）
   - `PullRequest`（含 `PullRequestComment`）
   - `Repository` 和 `User` 中添加反向关系
   - 注意：Repository 有两个 PullRequest 关系需要加 @relation name（"TargetRepo" / "SourceRepo"）
   - 注意：schema 注释不能含中文，否则 `prisma generate` 报 `Invalid character`

2. 执行迁移（复制 schema 到容器再 db push）：
   ```
   docker cp prisma/schema.prisma my-blog-app-1:/app/prisma/schema.prisma
   docker exec my-blog-app-1 npx prisma db push --skip-generate
   docker exec my-blog-app-1 npx prisma generate
   ```

3. 修复 issues/pulls API：将嵌套 author 对象展平为 `authorUsername` 字符串
4. 修复前端 page.tsx：interface 用 `authorUsername: string` 替代 `author: {...} | null`

### 结果
- 数据库新增 5 个表：Issue, IssueComment, IssueLabel, PullRequest, PullRequestComment
- issues/pulls API 正常返回 `{ code: 200, data: { items: [], total: 0 } }`
- 仓库页面恢复正常加载

## 修复全局响应缓慢 bug（2026-04-21 下午）

### 根本原因
**45 个 API 路由文件全部写了 `const prisma = new PrismaClient()`**，每次 Next.js 热加载/请求都会创建新的数据库连接池，导致 PostgreSQL 连接数耗尽，整个应用请求极慢甚至空白。

项目中已有正确的单例文件 `src/lib/prisma.ts`，但所有 API 路由绕过了它。

### 修复方案
用 Python 脚本批量替换所有 route.ts：
- 删除 `import { PrismaClient } from '@prisma/client';`
- 删除 `const prisma = new PrismaClient();`
- 添加 `import { prisma } from '@/lib/prisma';`

共修复 **45 个文件**，重启容器后恢复正常。

### 注意事项
- Next.js dev 模式下仍可能看到 "10th instance" 警告，是容器重启前历史日志遗留，不影响修复效果
- 今后新增 API 路由必须使用 `import { prisma } from '@/lib/prisma'`，禁止 `new PrismaClient()`

### ⚠️ 踩坑：数据库诊断不能随便跑大查询
今天排查时执行了一个不带 LIMIT 的大表查询，导致 PostgreSQL 读了 53K blocks（~420MB），CPU 飙到 87%、内存涨到 1.1GB，整个数据库被压垮。
**教训**：诊断时必须先加 LIMIT 或 WHERE 条件，避免全表扫描。严禁跑 `COPY`、`pg_dump`、无 LIMIT 的 `SELECT *`。

### 踩坑：Prisma findMany 禁止 select * —— RepoItem.content 可能存了 100MB+
**根本原因**：`tree` API 的 `findMany` 没有用 `select` 字段过滤，导致 Prisma 每次都把 `content` 字段（最大 133MB）从数据库拉到 Node.js 并 JSON 序列化，造成 5.8 秒的延迟。

**修复**：
1. `tree/route.ts`：`findMany` 加 `select` 显式排除 `content` 字段
2. `fork/route.ts`：同样问题 + 字段名写错了（`path`/`size`/`sha` 实际是 `fileHash`/`fileSize`），一并修复

**验证**：修复后 tree API 从 **5800ms → 430ms**，快了 13 倍。

## 仓库页面分支选择器重构

### 需求
将仓库页面工具栏的"main"从静态文字改为真正的分支选择器。

### 改动内容
1. **新增状态**：`currentBranch`（当前分支）、`branches`（分支列表）、`showBranchDropdown`（下拉开关）
2. **新增图标**：`GitBranchIcon`（分支图标）、`GitCommitIcon`（当前分支图标）
3. **初始化逻辑**：`useEffect` 从 `repo.defaultBranch` 读取默认分支，默认到 'main'；PR 模态框目标分支默认值同步为 `currentBranch`
4. **切换分支**：`handleSwitchBranch` 切换分支时重置 `currentPath` 为 `[]`，触发文件树重新拉取
5. **下拉菜单**：点击按钮展开分支列表，点击某分支切换，当前分支高亮显示

### 注意
- 仓库文件没有 `branch` 字段，所以这是纯 UI 层面的分支选择（数据层面仍是单分支）
- 后续如需真正多分支，需改 `repo_items` 表加 `branch` 字段
